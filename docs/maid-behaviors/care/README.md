# 照料、状态与反馈行为

本页描述女仆的饥饿、进食、回血、背包与工具状态，以及她如何向主人表达需求。

[返回行为总索引](../README.md)

## 独立饥饿与饱和度

每只女仆拥有独立于 TLM 旧字段的饥饿值、饱和度和消耗度，并随女仆 NBT 保存。

| 项目 | 内置默认值 |
| --- | ---: |
| 初始与最大饥饿值 | 100 |
| 初始饱和度 | 25 |
| 饱和度上限 | 不超过当前饥饿值，最高 100 |
| 自动进食阈值 | 40 |
| 工作消耗 | 每 200 tick 降 1 |
| 空闲消耗 | 每 400 tick 降 1 |
| 休息或睡眠 | 不消耗 |

活动先消耗饱和度，饱和度耗尽后才降低饥饿值。实体未加载时不追算离线消耗。
低饥饿不会直接扣血、减速或强制停止任务。

## 食物恢复

以下来源都会恢复附属饥饿：

- 主人对准女仆口部区域直接喂食。
- 女仆完成 Work Meal、Heal Meal 或 Home Meal。
- 附属自动进食。
- 主人喂食整块蛋糕。

普通恢复公式：

- 饥饿值增加：原版营养值 × 5。
- 饱和度增加：原版营养值 × 原版饱和系数 × 2 × 5。
- 饱和度不会超过当前饥饿值，也不会超过 100。

整块蛋糕按原版 7 片合计营养值 14 计算；创造模式保留效果但不消耗物品。

## 自动进食

饥饿值不高于 40 时，女仆按以下顺序寻找食物：

1. 当前手中的合法食物。
2. 可用背包中的合法食物。
3. 若本地无餐，寻找 8 格内柜内存有合法食物的 TLM 零食柜，走到 2 格内后只取一份。

三类来源都复用 TLM Work Meal 的食物处理器和黑名单。**"什么算合法食物"这一问比本体更宽**：
本体的判据是 `ItemStack.isEdible()`，读的是物品的静态食物属性，而 Forge 允许模组只实现
`getFoodProperties(stack, entity)`——按吃的人给属性。那类食物本体一个处理器都不认，表现
就是女仆对模组食物无动于衷。附属在**自己的**进食路径上补了一个兜底处理器：本体处理器
都不接、而 Forge 说它确实是食物时，仍用本体的默认工作餐流程把它吃掉。黑名单照问，也
不注册进 `MaidMealManager`——那是全局注册表，动它会连带改变其它工作模式。

零食柜由事件驱动 Affordance 索引
发现，再由确定性 Data Pack 意图执行，优先级为 60；Home 模式可以使用，但战斗、硬移动、
命令坐下、乘坐状态、物品使用或任务禁止进食时不会强行取餐。多名女仆先竞争具体柜槽
Claim，提交时再次核对物品指纹并只提取一份，不会复制物品。柜内没有合法食物时才继续
执行缺食求助流程。

## 饥饿与饱和度回血

女仆受伤且饥饿值高于 40 时，基础回血按三档运行：

| 饥饿值 | 基础回血 |
| --- | --- |
| 80–100 | 每 10 tick 恢复 1 点生命 |
| 60–79 | 每 80 tick 恢复 1 点生命 |
| 41–59 | 每 160 tick 恢复 1 点生命 |
| 0–40 | 停止附属回血，保留饥饿用于自动进食 |

每次基础回血成功后消耗 1 点饥饿。

饥饿值高于 40 且仍有饱和度时，另一套独立计时器每 10 tick 按玩家饱和回血公式执行。
两套计时器可以在同一 tick 生效，直到生命达到上限；进食和使用物品不会暂停计时。

TLM 服务端原有随机回血与治疗食物仍然保留。附属只取消客户端重复随机回血，
避免血条先增加又被服务端值覆盖。

## 缺食物反馈

### 近距离状态祈求

自动进食失败并成功显示一条新的缺食警告时，状态模块会提交一次有效期
1200 tick 的求食信号。信号满足主人在 8 格内、跟随模式、可移动、非战斗且未使用
物品等条件后，由意图 AI：

1. 走到主人 2 格内。
2. 看向主人。
3. 进入请求动作 60 tick。
4. 在主人离开、女仆睡眠/死亡或时间结束时恢复。

状态模块只提交信号，不直接启动动作；同类气泡处于重复冷却时不会重复提交。
Home、命令坐下等硬状态下仍可显示气泡，但不会形成可执行的求食意图。

### 主动求食

数据驱动意图 AI 还可让女仆主动走向主人：

- 饥饿值 ≤40：每 5 秒参与评估，候选胜出后有 10% 概率激活。
- 饥饿值 ≤20 且好感度等级 ≥3：每 5 秒参与评估，候选胜出后有 25% 概率激活。

缺食信号、普通求食和高好感求食统一复用同一个 Data Pack 计划，抵达后必经同一个
60 tick 请求动作；两条主动分支不保证先显示缺食气泡。战斗、Home、命令坐下、
物品使用和硬移动需求优先；内置定义没有工作目标保护，仍可能接管正在走向工作点的移动。
完整规则见[陪伴 AI、移动与座位](../companion/README.md)。

## 主动拾取掉落物

**开启拾物后，她会自己走过去捡。**本体一直会捡东西，但只在她身边
`maid_pickup_range`（默认 0.5 格）内——`EntityMaid.pushEntities` 每 tick 扫一圈。
缺的从来不是捡，是走过去：一场架打完，战利品散在她脚下三五格外，而在此之前没有
任何东西会让她挪一步。

附属只补走的那一半，捡仍然交回本体（`pickupItem`），所以拾取规则、音效、事件与
本体完全一致。

- **开关只有一处。**"她愿不愿意捡这件东西"由本体的 `canPickup` 回答，而那个谓词
  同时管着拾物开关、拾取类型（物品／经验／箭）、物品过滤名单，并**模拟一次插入**
  确认真的放得下。关掉拾物、背包塞满、或者物品在黑名单里，掉落物就不会被登记成
  广告，意图连"有东西可捡"都读不到。附属没有第二处判断。
  - "放得下"按本体的口径算：它模拟插入的是 `getAvailableInv(false)`，即
    **背包加两只手**——所以背包满了她仍可能把东西拿在手上，这是本体行为。
- 未驯服的女仆不捡，与本体自动拾取的条件（`isPickup() && isTame()`）一致。
- **经验球和 P 点一样会去捡。**本体的 `canPickup` 一直就认它们（走拾取类型里的
  `canPickXp()`），少的同样只是走过去那一半。与掉落物**登记成同一类商品**，所以
  她按距离一件件收、不分类别——分开排序会让她为了一颗远处的经验球放着脚边的
  铁锭不管。玩家把拾取类型设成"只捡物品"时，经验球不会被登记。
- **不挑贵的。**所有可捡物登记同一个价，排序整个交给距离：先捡最近的，一件接一件，
  路线自然是短的。给掉落物排价会让她越过脚边三件东西去拿远处那一件。
- **一件接一件，零 tick 间隔。**这是**一次激活清一片**，不是一次一件：收下一件
  之后差事不收工，下一 tick 直接找下一个目标接着走。地上清空时才结束。
  - 这一条不是参数调出来的。默认那种"一趟一件"的差事，每收一件都要走完
    "意图结束 → 编排器重新评估（最快 5 tick）→ 重新选中 → 重新找目标 →
    重新写移动目标"，**而这中间她没有移动目标，于是站住、再起步**。把冷却调成零、
    把评估间隔对齐到编排器自身的 5 tick 之后，那一停仍然在——它根本不在参数里。
  - 机制是 `Errand.sweeps()`，默认关闭。取一份饭、坐下、走到主人身边都该在做完
    那一件之后收工，只有清扫不是。
  - **收下一件的那一拍不清路径。**在那一拍抹掉移动目标，写回就要等下一 tick，
    中间隔着一次导航更新——她走到跟前刹住、收完再重新起步。留着的话，下一 tick 的
    `claim()` 会在**同一 tick 内**完成"取消旧的 + 写新的"。
  - 但**预订必须照常放掉**，否则下一 tick 为下一件 `tryClaim` 会拿不到，整趟当场
    失败：量到的样子是她收下第一件、走了九个 tick，然后再也不动。
  - **"到了没有"必须和导航用同一把尺。**原版的移动行为按**方块曼哈顿距离**判到达、
    到了就停，而动手的条件此前用的是欧氏距离——曼哈顿为一时欧氏可以接近二，于是
    她停在东西旁边却永远够不到动手的门槛，就那么站着。实测：清扫意图活动着、静止
    五百三十一 tick，二十件只收到一件。
  - **一件够不着的东西不许挂死整趟。**"每 tick 重挑最近的那一件"遇上够不着的东西
    会每次都挑中它——实测最后一件卡住之后她原地站了四百二十 tick。放弃的判据有两条：
    导航报 `CANT_REACH_WALK_TARGET_SINCE`（即时），或者盯着同一件超过五秒还没收到
    （有些够不着不表现为寻路失败——路是通的，只是终点在她头顶）。放弃过的记一小批
    （八件），三十秒后再考虑；只记一件时她会在两件够不着的东西之间来回。
- **够不着的东西不去够，跳一下够得着的才去——而且她真的会跳。**
  - 上限按她自己的身板算：身高 + 拾取半径（属性，本体默认 0.5）+ 一跳（1.25 格）。
    没有这一条时她会走到头顶三格那件东西的正下方反复判断"到了没到"，**看起来就是
    在原地点头**。上限也不能卡太紧，否则她会放着脚边台阶上的东西不管。下方不设限
    ——往下她走得到、掉得下去。
  - **把跳跃算进判据并不会让她跳。**原版只在寻路要迈台阶时才跳，而悬在两格高处的
    东西没有路可走：寻路当场报走不到，差事把它丢掉，实机看是"对着明明够得到的东西
    毫无反应"。所以走向途中要补一次起跳（`Errand.whileApproaching`，默认空实现），
    站到它正下方半格内、且在地面上才起跳。捡仍然是本体的——跳到顶点时她的碰撞箱
    加拾取半径正好罩住它。
  - 起跳门槛是**高过头顶**，不是高过"头顶加拾取半径"。那半格是碰撞箱擦着才算数的
    一段：正好两格高的东西落在它的边界上，站着够不到（相切不算相交），又不满足
    起跳条件，于是她既不跳也拿不到，杵在下面。
  - **要跳的那一档还得能站到正下方。**拾取判定是碰撞箱外扩拾取半径，半宽只有零点
    八格左右——跳得再高也够不到水平一格外的东西。所以东西摆在两格高实心柱子顶上时
    它是**真的拿不到**：她走不进那一格，只能停在旁边。不加这一条的表现就是她走到
    柱子边上一通蹦、五秒后放弃。地面上的和一格台阶上的（那一档不用跳，直接走上去）
    不受影响。
- **"附近有没有东西可捡"这一问不走广告板，直接扫实体。**其余感知走广告板是因为
  它们问的是方块（柜子、椅子），每人各扫一遍世界太贵；掉落物不是那种问题，它就是
  身边的一圈实体，原版也是直接扫的。送进广告板的代价量过：观察节流（20 tick 一次）、
  广告存活期（60 tick）、索引每 tick 的检查预算（下限 8 条）三样叠起来，**她收了
  几件之后就对满地的东西视而不见**。
- **走路时顺手收。**她在走向任何目标的途中（跟随、赶路、别的差事），臂展内（拾取
  半径外再半格）的掉落物会被顺手收走——不绕路、不停步、不碰移动目标。这是资源仲裁
  的最小实例：脚归当前意图，空闲的手可以被路边的机会借走（`TlmEnRouteScoop`）。
  打斗中不借，站着不借（那是清扫意图自己的事）。
- 量的方式见 `LooseDropContinuityGameTests`（二十件同种、散落、不合并，逐 tick 记
  "她动没动 + 当时谁占着她"）。三处修改各自值多少：

  | 改动 | 静止 tick | 其中清扫自己 | 收集 |
  |---|---|---|---|
  | 最初 | 591 | 531 | 1/20 |
  | + 到达判据与导航对齐 | 267 | 10 | 20/20 |
  | + 掉落物改直接扫 | **6** | **2** | 20/20 |
- **刚落地的经验球收不走。**本体的 `pickupXPOrb` 要求它至少活过两 tick（原版留给
  经验球互相合并的窗口），而 `canPickup` 不查这一条。所以判据里补了一遍——不补的话
  她会一路走到跟前、伸手、空手而归。P 点同理（抛掷计时要走完）。
- 意图类别为 LEISURE：战斗、进食、跟随、回家任何一个都能打断它，而打断没有代价
  ——东西还在原地，回头再来。因此**这条行为只在平静下来之后才看得见**，条件里写着
  `attack_target_present == 0` 与 `panic_active == 0`。
- 路上背包被装满、或者东西被别人捡走，她当场放弃这一趟，不会走到跟前才发现白跑。

## 背包已满反馈

女仆尝试拾取合法物品、但可用物品栏完全无法接收时，显示：

> 背包满了，捡不了……

以下情况不会误报：

- 物品在拾取黑名单中。
- 仍有拾取延迟。
- 物品入水、死亡或超出合法范围。
- Forge/TLM 事件明确拒绝拾取。
- 背包仍可接收部分或全部物品。

该反馈不改变拾取路径，只向主人说明失败原因。

## 低耐久工具

状态行为每 20 tick 检查女仆主手和副手，不检查护甲或饰品。

警戒线为：

`剩余耐久 ≤ max(10, 最大耐久的 10%)`

### 有备用工具

1. 扫描女仆可用背包。
2. 只选择相同物品 ID、且高于警戒线的工具。
3. 多个候选中选择剩余耐久最高者。
4. 新工具放入原手，旧工具回到候选槽位。
5. 女仆挥动对应手，并显示更换成功确认。

正在使用物品时不交换，避免打断弓、食物等流程。

### 没有备用工具

- 女仆保留原工具并继续当前工作。
- 显示带剩余耐久比例的进度气泡。
- 主人在 8 格内时进入 60 tick 祈求动作。
- 工具祈求优先于同时出现的缺食祈求。

## 状态聊天气泡

| 状态 | 表现 |
| --- | --- |
| 缺食物 | 文本气泡 |
| 背包已满 | 文本气泡 |
| 工具低耐久 | 耐久比例进度气泡 |
| 自动换工具成功 | 文本确认气泡 |
| 饱和度已满 | “已经吃不下了……”拒绝气泡 |

前四类由周期状态反馈产生；饱和度已满气泡只在主人喂食被拒绝时产生。

普通状态气泡：

- 默认显示 15 秒。
- 同类警告默认冷却 60 秒。
- 优先级为 -1，不挤掉 AI waiting 或回复气泡。
- 只删除本功能自己记录的气泡。

饱和度已满的拒绝动作与音效使用 20 tick 冷却，气泡存在时不重复添加。

## 数据与边界

- 饥饿、饱和度和消耗度随女仆保存并同步。
- 气泡 key、重复冷却和动作计时只保存在服务端运行时。
- 气泡通过 TLM `ChatBubbleManager` 同步。
- 祈求动作通过 TLM `DATA_BEGGING` 同步。
- 本功能不会替换 TLM 随机表情池。
