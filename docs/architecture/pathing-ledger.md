# 寻路 GameTest 欠账台账：为什么红数四十轮不动

这份台账起因于一句质问："为什么问题总是反复出现？已经第 145 次测试了，每次都是修了
又增，恐怕到 300 次都结束不了。"

方向是对的，但把 78 轮日志摊开之后，机理和双方的印象都不一样。**不是修一个捅一个，
是同一批场景钉死了四十轮没人动过。**

## 0. 证据

`tools/gametest_ledger.py` 扫全部轮次日志，只采信**收官轮**（日志里有
`N required tests failed` / `All required tests passed`）。被停摆或硬顶截断的轮次会
报出虚假的低红数——早先就有一次把截断轮的"5 红"当成进展，真实基线是 12 红。

跨越 sw105..sw144（四十轮），红数一直在 5–7 横盘。**真回归总共只有 4 例**，其中两例

卡死、测试基建上，那些确实必要，但欠账清单没动。

`pastafencepostonthenarrowwalkshesqueezes` 是四十轮里**第一个**转绿的核心欠账。

## 1. 为什么我一直没发现

每轮只看两个数：总红数，和红榜快照。这两个数看不出：

- 某场景红了四十轮**没被碰过**（红榜里它一直在，看起来像"还没轮到"）
- 这一刀**捅坏了**什么（新红混在红榜里，与老红长得一样）
- 哪些红是**偶发**（同场景多副本，随机失败），不值得当回归追

三者混在同一个数字里，每次都要靠人重新分辨，而且总是慢几轮才分辨出来。

## 2. 机制（现在自动做这件事）

```bash
py -3 tools/gametest_ledger.py table <日志目录> --last 12
```

```bash
py -3 tools/gametest_ledger.py diff <日志目录> sw145
```

`diff` 与上一个**收官轮**逐场景比对，输出三类：

| 标记 | 含义 | 该怎么办 |
|---|---|---|
| `NEW RED` | 上轮绿、这轮红 | **这一刀捅的**，优先查 |
| `FIXED` | 上轮红、这轮绿 | 记进本文件的欠账表 |
| `STILL RED` | 两轮都红 | 长期欠账，看它有没有在攻坚清单里 |
| `(flaky)` | 同一轮内多副本红绿不一致 | 执行余量问题，不是回归，别当回归追 |

flaky 用的是**同轮证据**（`_run7` 红而 `_run8` 绿，同一次构建、同一个世界），不是跨轮
翻转——跨轮翻转分不出"刚修好"和"刚弄坏"，两者翻转的样子一模一样。

`round.sh` 收官后自动跑一次 `diff`，不必记得手动跑。

### 两个盲点（sw149 补上）

**一、"没跑"和"绿了"长得一模一样。** 通过的场景**不往日志里写任何一行**，所以
"grep 不到这个名字"既可能是它绿了，也可能是它压根没跑——我拿后者下过一次结论，是
错的。而 `N required tests failed` 在提前收场的轮次里照样打印，挡不住这种误读。唯一
硬凭据是完成横幅 `====== N GAME TESTS COMPLETE ======`：它带着**跑了多少个**。现在
diff 第一行就报 `(485 -> 486 tests ran)`，测试数下降会直接警告"FIXED 存疑"。

**二、红种数看不见"变严重了"。** 同一场景红的副本从 1 个涨到 3 个，红种数纹丝不动
（细柱案 sw147→sw149 正是如此）。现在 `STILL RED` 会附 `1 -> 3 copies WORSE`。

## 5. 测试基建：批次之间世界不还原

围栏角案追到最后，根因不在寻路，在测试基建。而且**中间还错了一次**，值得连错法一起
记下来。

先怀疑的是"场地互相覆盖"：棋盘两轴步长都是十三，多个场景铺地远超这个范围，本场写
出去的方块落进邻场领地。收口 x 方向之后（sw152）——**没修好，供词一字不差**。

真相由读数带的俯视图给出：她四周整片都是立障（`|`，同图例下末地烛也是这个符号），
可这场的栅栏只在 3..11，她站的西北矮地一根都不该有。**GameTest 在批次之间不还原
世界**：本场只写地面（`DECK-1`/`DECK`）与场沿（`DECK+1/+2`），没写到的格子留着上
一批的栅栏。谁红只由棋盘位置上先跑的是谁决定——所以它五轮来一直伪装成间歇病，也
正好解释了四个副本只有一个中招。

**修法**：建场前先把本场范围清空（`DECK-1..DECK+3` 全设 AIR），再铺地放栅栏。

越界这件事本身仍然要收（它是**另一条**污染路径，只是不是这次的凶手）：

已知越界（`grep "for (int [xz] = -"` 于 `gametest/pathing/patrol/`）：

| 文件 | 范围 | 危害 |
|---|---|---|
| `FencePenGameTests` 四处 | `x,z = -2..16` / `-2..14` | **已全部收到 0..12**。带高度差的三处最危险（会把邻场地面抬高或压低一格，考题当场改写）；`outOfTheFencePenSheFindsTheGap` 另有约束——注释记着"西沿只留两格会偶发踏空摔"，所以是把**圈**挪了一格（圈心 5,5→6,6），东西各留三格绕行地，考题一字未动 |
| `PenRouteGameTests` 89 | `x,z = -8..24` | **已收窄**：圈本身十三见方（大圈是考题，不能缩），场地必然溢出步长，只能少溢——33×33 收成"绕行环 + 走廊"，面积降到不足四分之一，且溢出部分只有单一高度的草 |
| `StepIslandGameTests` 162/235 | `x = 0..17` | 未收 |
| 其余若干 | `-1..N` | 只多铺一格地面，暂无实害 |

带 **BARRIER / 栅栏 / 高度差**的越界才真正危险——它们会改变邻场的地形语义。纯铺地
的越界目前无害，但同一块地被两个场写两次，哪天高度口径一变就会变成下一桩"红绿由
邻位决定"。

**假设已验证**：sw153 全绿（`All 486 required tests passed`，486 tests ran，16 分钟、
过载 11，都是五十轮里最好的一次）。

**清场该推广，但不该顺手推**。共用辅助已就位（`gametest/support/world/Arena.java`，
`BridgePatrol` 已 500 行顶格放不下），围栏角改用了它。其余 patrol 场景吃的是同一份
遗产，现在绿只是上一批恰好没在要害位置留东西——但推广要逐场景定清场范围（各文件
`DECK` 从 2 到 9 不等，`intoTheCornerGap` 还会往下填到 `DECK-3`），清多了会连世界地
表一起清掉、清少了等于没清。这是十几处各不相同的改动，值得单独一轮做、单独验，不
适合在刚拿到 0 红的这一轮里顺手带上。

## 6. 配速链：一个从没有过真值的字段

玩家实机报"女仆不会奔跑了"，追下来是自有执行器直写 {@code deltaMovement}，把原版
那条 **`MoveControl` → 倍率 × MOVEMENT_SPEED → `travel()`** 整个绕了过去：倍率与
属性都不参与，她只剩一档手调的 0.16 格每 tick（3.2 格每秒，比玩家走路的 4.3 还慢，
比冲刺的 5.6 慢四成）。跟随跟不上、战斗撤不开被怪追上，是同一个根。

修它的过程连栽三跤，**三跤是同一个形状**：`PathNavigation.speedModifier` 只有
`super.moveTo` 会赋值，而自有分支从不走那条路——它一直是 0，而"一直是 0"这件事被
三处代码当成了前提。

| 跤 | 症状 | 真相 |
|---|---|---|
| 一 | 实机"完全无法行动" | 直接读 `pace()` 配速，而它恒为 0 → 步速 0 |
| 二 | 走路慢四成，细柱十副本全摔 | 用 `当前属性 ÷ 基准属性` 当系数，实测 ≈0.73（属性被压过），等于在未知上乘一刀 |
| 三 | 步速已回基准，细柱仍十副本全摔 | 飞行控制 `setWantedPosition(..., aloft ? nav.pace() : …)` ——**整套弹道是在零推力下标定的**，倍率一接上它就开始推，落点全偏 |

**教训**：接一个从没被人读过的字段之前，先查清它现在是什么值、以及**谁在依赖它现在
的值**。第三跤尤其阴——那行代码写的是"滞空按步速推"，读起来完全合理，可它从未真正
推过。

排查过一遍：另外三个读 `nav.pace()` 的组件（`Leaper`、`LaneWork`、
`SegmentedPathwalk`）都挂在旧执行器下，只在**非自由模式**跑，那条链走 `super.moveTo`、
`speedModifier` 一直正常，不受影响。

**钉子**：`anOrderOnItsOwnGetsHerMoving`（`ColdStartGameTests`）。整批测试盖不住这个
洞——驱动写 `WalkTarget` 走原版 sink 的 `moveTo(Path, speed)`，那条链上倍率是有值的；
这颗钉子专走实机用的坐标版 `moveTo(x,y,z,speed)`。

## 7. 轮次耗时基线

"测试越到后面越慢"提过一次，此后每轮记一笔，免得下次又靠印象讨论性能。

| 轮次 | 耗时 | 过载 | 备注 |
|---|---|---|---|
| sw142 | 36 min | 14 | |
| sw143 | 23 min | 14 | |
| sw144 | 31.5 min | 13 | 碰撞皮厚 |
| sw145 | **20 min** | 12 | 车道跳（新增 21 档弹道扫描） |
| sw146 | **17 min** | 13 | turning 跳降豁免 |
| sw147 | 23.5 min | 14 | 起点认脚下支撑（捅了围栏角回归） |
| sw149 | **17.8 min** | 16 | 跨格判据 + 窄面判到 + 过路费撤零 |
| sw150 | 17 min | — | 起点锚按支撑归格（细柱转绿） |
| sw153 | **16.2 min** | 11 | 清场 + 场地收口 → **全绿 486/486** |

新增的车道扫描没有让整轮变慢，反而是最快的两轮。两条原因：中线阻挡粗筛把
21 档弹道挡在常态之外（只有"直线上确实有东西挡着"的边才展开）；而修好一个
卡死场景本身就是提速——卡住的场景要跑满 320 tick 超时才收场。

**修欠账 ＝ 提速**，这条值得记住：性能与欠账不是此消彼长的两件事。sw142 的 36 分钟
里有大半是六个卡死场景在跑满超时；六笔清完之后，整轮稳定在 17–18 分钟。

## 8. 维护约定

- 每轮收官后读 `diff` 输出，`NEW RED` 当轮查清，不留到下一轮
- 欠账表每有一行转绿，就在"状态"栏写清是**哪一刀**修的，便于回归时倒查
- 截断轮（`CUT SHORT`）的红数不作数，也不写进本表
