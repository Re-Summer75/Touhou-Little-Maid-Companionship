# 寻路 GameTest 欠账台账：为什么红数四十轮不动

这份台账起因于一句质问："为什么问题总是反复出现？已经第 145 次测试了，每次都是修了
又增，恐怕到 300 次都结束不了。"

方向是对的，但把 78 轮日志摊开之后，机理和双方的印象都不一样。**不是修一个捅一个，
是同一批场景钉死了四十轮没人动过。**

## 0. 证据

`tools/gametest_ledger.py` 扫全部轮次日志，只采信**收官轮**（日志里有
`N required tests failed` / `All required tests passed`）。被停摆或硬顶截断的轮次会
报出虚假的低红数——早先就有一次把截断轮的"5 红"当成进展，真实基线是 12 红。

跨越 sw105..sw144（四十轮），红数一直在 5–7 横盘。**真回归总共只有 4 例**，其中两例

卡死、测试基建上，那些确实必要，但欠账清单没动。

`pastafencepostonthenarrowwalkshesqueezes` 是四十轮里**第一个**转绿的核心欠账。

## 1. 为什么我一直没发现

每轮只看两个数：总红数，和红榜快照。这两个数看不出：

- 某场景红了四十轮**没被碰过**（红榜里它一直在，看起来像"还没轮到"）
- 这一刀**捅坏了**什么（新红混在红榜里，与老红长得一样）
- 哪些红是**偶发**（同场景多副本，随机失败），不值得当回归追

三者混在同一个数字里，每次都要靠人重新分辨，而且总是慢几轮才分辨出来。

## 2. 机制（现在自动做这件事）

```bash
py -3 tools/gametest_ledger.py table <日志目录> --last 12
```

```bash
py -3 tools/gametest_ledger.py diff <日志目录> sw145
```

`diff` 与上一个**收官轮**逐场景比对，输出三类：

| 标记 | 含义 | 该怎么办 |
|---|---|---|
| `NEW RED` | 上轮绿、这轮红 | **这一刀捅的**，优先查 |
| `FIXED` | 上轮红、这轮绿 | 记进本文件的欠账表 |
| `STILL RED` | 两轮都红 | 长期欠账，看它有没有在攻坚清单里 |
| `(flaky)` | 同一轮内多副本红绿不一致 | 执行余量问题，不是回归，别当回归追 |

flaky 用的是**同轮证据**（`_run7` 红而 `_run8` 绿，同一次构建、同一个世界），不是跨轮
翻转——跨轮翻转分不出"刚修好"和"刚弄坏"，两者翻转的样子一模一样。

`round.sh` 收官后自动跑一次 `diff`，不必记得手动跑。

### 两个盲点（sw149 补上）

**一、"没跑"和"绿了"长得一模一样。** 通过的场景**不往日志里写任何一行**，所以
"grep 不到这个名字"既可能是它绿了，也可能是它压根没跑——我拿后者下过一次结论，是
错的。而 `N required tests failed` 在提前收场的轮次里照样打印，挡不住这种误读。唯一
硬凭据是完成横幅 `====== N GAME TESTS COMPLETE ======`：它带着**跑了多少个**。现在
diff 第一行就报 `(485 -> 486 tests ran)`，测试数下降会直接警告"FIXED 存疑"。

**二、红种数看不见"变严重了"。** 同一场景红的副本从 1 个涨到 3 个，红种数纹丝不动
（细柱案 sw147→sw149 正是如此）。现在 `STILL RED` 会附 `1 -> 3 copies WORSE`。

## 5. 测试基建：批次之间世界不还原

围栏角案追到最后，根因不在寻路，在测试基建。而且**中间还错了一次**，值得连错法一起
记下来。

先怀疑的是"场地互相覆盖"：棋盘两轴步长都是十三，多个场景铺地远超这个范围，本场写
出去的方块落进邻场领地。收口 x 方向之后（sw152）——**没修好，供词一字不差**。

真相由读数带的俯视图给出：她四周整片都是立障（`|`，同图例下末地烛也是这个符号），
可这场的栅栏只在 3..11，她站的西北矮地一根都不该有。**GameTest 在批次之间不还原
世界**：本场只写地面（`DECK-1`/`DECK`）与场沿（`DECK+1/+2`），没写到的格子留着上
一批的栅栏。谁红只由棋盘位置上先跑的是谁决定——所以它五轮来一直伪装成间歇病，也
正好解释了四个副本只有一个中招。

**修法**：建场前先把本场范围清空（`DECK-1..DECK+3` 全设 AIR），再铺地放栅栏。

越界这件事本身仍然要收（它是**另一条**污染路径，只是不是这次的凶手）：

已知越界（`grep "for (int [xz] = -"` 于 `gametest/pathing/patrol/`）：

| 文件 | 范围 | 危害 |
|---|---|---|
| `FencePenGameTests` 四处 | `x,z = -2..16` / `-2..14` | **已全部收到 0..12**。带高度差的三处最危险（会把邻场地面抬高或压低一格，考题当场改写）；`outOfTheFencePenSheFindsTheGap` 另有约束——注释记着"西沿只留两格会偶发踏空摔"，圈心因此两度搬家：5,5→6,6（西沿三格，sw177 `run2` 仍在 rel −0.67 摔出场沿）→7,7（西沿四格，sw178 起稳绿）。西沿那四格是拿摔换来的，不能省 |
| `PenRouteGameTests` 89 | `x,z = -8..24` | **已收窄**：圈本身十三见方（大圈是考题，不能缩），场地必然溢出步长，只能少溢——33×33 收成"绕行环 + 走廊"，面积降到不足四分之一，且溢出部分只有单一高度的草 |
| `StepIslandGameTests` 162/235 | `x = 0..17` | 未收 |
| 其余若干 | `-1..N` | 只多铺一格地面，暂无实害 |

带 **BARRIER / 栅栏 / 高度差**的越界才真正危险——它们会改变邻场的地形语义。纯铺地
的越界目前无害，但同一块地被两个场写两次，哪天高度口径一变就会变成下一桩"红绿由
邻位决定"。

**假设已验证**：sw153 全绿（`All 486 required tests passed`，486 tests ran，16 分钟、
过载 11，都是五十轮里最好的一次）。

**清场该推广，但不该顺手推**。共用辅助已就位（`gametest/support/world/Arena.java`，
`BridgePatrol` 已 500 行顶格放不下），围栏角改用了它。其余 patrol 场景吃的是同一份
遗产，现在绿只是上一批恰好没在要害位置留东西——但推广要逐场景定清场范围（各文件
`DECK` 从 2 到 9 不等，`intoTheCornerGap` 还会往下填到 `DECK-3`），清多了会连世界地
表一起清掉、清少了等于没清。这是十几处各不相同的改动，值得单独一轮做、单独验，不
适合在刚拿到 0 红的这一轮里顺手带上。

## 6. 配速链：一个从没有过真值的字段

玩家实机报"女仆不会奔跑了"，追下来是自有执行器直写 {@code deltaMovement}，把原版
那条 **`MoveControl` → 倍率 × MOVEMENT_SPEED → `travel()`** 整个绕了过去：倍率与
属性都不参与，她只剩一档手调的 0.16 格每 tick（3.2 格每秒，比玩家走路的 4.3 还慢，
比冲刺的 5.6 慢四成）。跟随跟不上、战斗撤不开被怪追上，是同一个根。

修它的过程连栽三跤，**三跤是同一个形状**：`PathNavigation.speedModifier` 只有
`super.moveTo` 会赋值，而自有分支从不走那条路——它一直是 0，而"一直是 0"这件事被
三处代码当成了前提。

| 跤 | 症状 | 真相 |
|---|---|---|
| 一 | 实机"完全无法行动" | 直接读 `pace()` 配速，而它恒为 0 → 步速 0 |
| 二 | 走路慢四成，细柱十副本全摔 | 用 `当前属性 ÷ 基准属性` 当系数，实测 ≈0.73（属性被压过），等于在未知上乘一刀 |
| 三 | 步速已回基准，细柱仍十副本全摔 | 飞行控制 `setWantedPosition(..., aloft ? nav.pace() : …)` ——**整套弹道是在零推力下标定的**，倍率一接上它就开始推，落点全偏 |

**教训**：接一个从没被人读过的字段之前，先查清它现在是什么值、以及**谁在依赖它现在
的值**。第三跤尤其阴——那行代码写的是"滞空按步速推"，读起来完全合理，可它从未真正
推过。

排查过一遍：另外三个读 `nav.pace()` 的组件（`Leaper`、`LaneWork`、
`SegmentedPathwalk`）都挂在旧执行器下，只在**非自由模式**跑，那条链走 `super.moveTo`、
`speedModifier` 一直正常，不受影响。

**钉子**：`anOrderOnItsOwnGetsHerMoving`（`ColdStartGameTests`）。整批测试盖不住这个
洞——驱动写 `WalkTarget` 走原版 sink 的 `moveTo(Path, speed)`，那条链上倍率是有值的；
这颗钉子专走实机用的坐标版 `moveTo(x,y,z,speed)`。

## 8. 一条记错的账

`shejumpsforwhat…armsreach` 在欠账表上挂了四十轮，被当成"她不会为够不着的东西起
跳"。五轮读数逐个排除下来才发现：她走到、判据放行、状态门开着、正下方是空的，**而
东西在她走到之前就进了她的包**。红的不是行为，是场景——物品摆得太低，本体走近就收
了。

**教训**：一个场景连红很久而每次诊断都指向不同的地方时，先怀疑题目本身。判据链上每
一环都"看起来对"，往往说明问的问题不对。这次是靠逐 tick 记账（起跳窗口、竖直速度、
差事返回值、目标可收性、物品存活）一格一格逼出来的——每加一层读数就排除一个假设，
没有一次靠改参数撞。

## 9. 实机欠账（测试盖不住的）

sw167 全绿（487/487）之后的实机跑动，暴露了两笔测试场景里出不来的问题。共同点是
**测试的目标是固定的，实机的目标（主人）会动**。

**一、车道跳在同一对点之间横跳。**

```
[voxel-lane]  0.531  -58.5 → -56.5
[voxel-lane] -0.500  -56.5 → -58.5     ← 又跳回来
```

单次车道跳是对的（两条钉子都绿），可跟随一个移动的主人时，目标每变化一格多就触发
重铺（`moveTo` 的同单节流阈值是 1.0 格），而**跳跃是不可逆的承诺**——走错两步可以
走回来，跳错一次就得再跳一次。待查：跳边是否该要求"目标在若干 tick 内稳定"，或者
把承诺成本算进定价。
**（sw182 后大概率已缓解**：横跳的前提是平地上跳边与走链同价，供边闸门"走得通就
不跳"直接抽掉了这类跳边——那对往返点之间是平地。待实机复验后销账。）

**二、到了导航目标之后没人再下单。**

```
frozen 200t at (-47.4, 72.0, 608.5)
nav(done=true, to=(-48, 72, 608))   walk=-   ownerDist=13.2
```

导航确实到了它被给的那个点（差 0.6 格），`walk=-` 说明此后上层没再写移动目标，而她
离主人 13.2 格。**问题在意图层不在脚下**——但供词里没有意图侧的读数，查它需要先把
"当时哪个意图在跑、为什么不跟随"打出来。

## 10. 寻路性能基准（sw168 基线）

玩家问"几十只女仆扛不扛得住"，此前没有任何数字。两条基准局补上：
`PathPlanBenchmarkGameTests`（规划裸开销，按地形分档）与
`PathCrowdBenchmarkGameTests`（真女仆的规模开销，读服务器 tick）。
`COMPANIONSHIP_BENCHMARK=1` 才跑，平时那一轮不受影响。

**规模**（MC 一 tick 的预算是 50ms）

| 只数 | tick 中位 | 最坏 | 占预算 |
|---|---|---|---|
| 1 | 2.56ms | 19.71ms | 5% |
| 8 | 34.05ms | 78.52ms | 68% |
| 24 | **61.56ms** | 78.66ms | **123%** |

**规划**（直接调 `VoxelAstar.find`，不走节流与配额）

| 地形 | 中位 | 最坏 | 站数 |
|---|---|---|---|
| 空地 8 格 | 0.95ms | 1.02ms | 5.0 |
| 空地 32 格 | 3.83ms | 6.74ms | 17.0 |
| 栅栏迷宫 | 4.31ms | 4.69ms | 8.0 |
| 跑酷／车道 | 5.06ms | 5.73ms | 14.0 |

**诊断出三层，性质不同**：

1. **节流有洞**（已修）。同单节流的前提是"**还有活路**"，路一走完就整个失效，而
   上层每 tick 还在下同一个单——她到了目的地反而开始每 tick 重铺。
   `8 × 4.31ms ≈ 34ms` 与实测分毫不差。实机最常见的姿势正是这个：几只女仆跟到主
   人身边站定，个个空转重铺。
2. ~~**拉直没吃满**~~ **诊断已被 sw180 推翻**：那 17 站不是没拉直的走链，是
   **16 段两格小跳**——快照层量出平地全程 `moves=LEAP`（见欠账表"快照三钉"）。
   `straighten` 与 4.5 格封顶都是无辜的：全是跳边，根本没有走链可拉。改修跳边
   定价／供边的不对称。
3. **单次规划的底子贵**（结构性）。空地直线都要 1ms，因为每条边都过扫掠仿真——这
   是亚格能力换来的代价，能优化但不会消失。原版 A* 同规模通常在 0.1ms 量级。

**基准轮自己的性质**：它把服务器压到 61ms，同轮别的测试会跟着超时红（sw168 有两
条，普通轮同场景是绿的）。战斗基准靠"每局独占 batch"避免互相干扰，可 **tick 时间
是全局的**，独占 batch 挡不住。所以基准轮的红数不能和普通轮直接比。

**量法返工两次（sw177/sw178），教训都进了测试章程**：

- **账串了**（sw177 暴露）。第一版计时挂在 `VoxelAstar` 静态入口上，账是全局的
  ——对照组明明不走自有引擎，却记到 19 次规划、455ms/次的假数（同 JVM 里别的批
  次在铺路）。改成 `PathClock` 按 UUID 分账后，sw178 里 stock 的 `plan 0.00ms/0`

- **tick 墙钟通道量的是整台服务器，不是我们**。sw178 实测自相矛盾：ours n=8
  p50 373ms 反而高于 n=24 的 56ms，stock 单只 334ms——邻批次收尾、GC、结构清理
  全掺在里面。**对比以 `pathcost`（分账）通道为准**，tick 行只当服务器语境读。
- 分账通道下的真实开销（sw178）：ours 单只 per-maid-tick 0.16ms、八只 0.10ms；
  二十四只涨到 1.46ms——plan 5.5s/348 次 ≈ **拥挤下单次规划 15.8ms**（被 23 只
  同伴堵死的搜索要耗尽预算才认输），这是 n=24 档的真账，比"节流洞"深一层。

## 11. 沿口手感与批次轮盘（sw187–193）

实机报了两笔手感账：跟随时**忽然瞬间停顿**、沿口下方块**抽搐不下去**。修理与
连锁如下——五个教训各有一行。

- **停顿的根**：到站节流把"路走完"一律当"人到了"。修成**运动感知**：末段而
  单子已漂（>0.3 格）窗缩到 3 tick 提前换路；路尽但人离单子还远（>1.5 格）同
  样只留 3 tick——长窗只罚真到站的防空转。
- **沿口不许拿验收的尺子治**（sw188 十一红的学费）：把图侧到站验收的竖直带收
  紧成非对称（上方半格），杆顶锚永远高过路标 y，杆桥类目标从此验收永不放行、
  部分路径再被降边剪刀截住。已回滚；拾取跳同轮被执行侧的非对称销账拦住起跳，
  一并回滚即愈。
- **共享批次是公共财产**：沿口新钉挤进 windingpatrol，同批打包挪位＋后续批次
  在同格继承了它的 DECK+1 石台，杆桥与玻璃行连坐（sw188/189）。独立成批＋收
  场自清后复原。**基准家族随后全员补了出场扫**——进场清保护自己，出场扫还别
  人干净格子，两半缺一不可。
- **批次执行顺序是轮盘**：批次集不变的两轮（sw190/191）杆桥红绿互换、与玻璃
  行反相关。不清场的场景在轮盘下轮流中奖——根治是把清场推广到全部 patrol 场
  景（§5 预告过的"值得单独一轮"，仍欠着）。
- **"差 N 格"同距跨格复现 ⇒ 时间不是地形**：杆桥三副本在三个不同棋盘格停在
  同样的"差 6~7 格"——三个前任留一模一样的垃圾不可能。对表耗时即破：轮子
  ≤1300s 全绿、≥1600s 全红（sw186/190 绿，sw191/192 红；sw192 跑在宿主忙时，
  2302s）。**杆桥是载荷余量最薄的一族**，慢轮的红先查耗时再查代码。

**悬案完结（sw193 破案、sw194 定谳）——真凶是原版 sink 的探路否决权**。
杆桥读数带一锤定音：`t42 写走目标 → t43 被擦`，全场十五次写入次次如此，
note/path 恒 `-`——体素引擎**从没接到过单**。机制：`MoveToTargetSink` 下单前
拿 `createPath`（原版 A*）探可达性，探不出就当场擦掉走目标；末地烛杆桥在原版
A* 眼里是绝路，真正会走的引擎连上场机会都没有。判决还会漂：原版探路半径按
FOLLOW_RANGE 摊开、扫得进邻场，PinSpread 副本数每轮变、批内打包随之挪位——
同一场景红绿由邻居决定（sw188–193 杆桥与玻璃行反相关翻红的全部解释）。玻璃
行/之字梯的 76 tick 冻结是同一支枪：lastPlan=76t 配零 fail，因为擦单发生在
**导航之外**，任何账都不会留。此前的配额指控（sw191 零拒单）就此撤销。

**修法＝探路权移交**（`VoxelAstar.toward`）：自由模式下 `createPath` 的答卷
由体素引擎出——铺得出交影子 Path（canReach=true），空中目标先落地（贴脚八
格），铺不出交诚实的 null。sink 的否决权废除，影子只答问询、执行仍走 moveTo
重规划。sw194 杆桥四场＋拾取撒豆当轮全部转绿，sw195 复确认。拒单供词
（diary `deny=N/Mt`）、`[voxel-quota]`/`[voxel-brake]` 取证与强闯保险
（连拒二十 tick 无视配额铺一次）作为长驻监听保留。

**探路官尾声（sw196/197）**：给"战斗站桩、拾取一顿一顿"的实机报案下过一次

## 12. 掉落物风暴：拾取卡顿的分账与治理（sw213–218）

实机报案"掉落物很多时她捡东西全服卡顿（非帧数），栅栏格内更明显"。为它立了
常驻基准 `PickupStormBenchmarkGameTests`（三臂：alone=原版底噪 / open=我们的
链 / fenced=放大器；240 件、进出双清、收场全销毁）。

**定罪链**：tick 落后 2161ms 实锤 → 我们的表（quota/brake/maid-hot）全零 →
jcmd 定点抽样（盯批次名开火）**十二抽十一中在 `VoxelAstar.find`，全部从
`MoveToTargetSink.start` 进来**——探路连发：sink 每 tick 换单每次全额规划，
且探路**既不走 PathClock 的账也不受 15ms 配额**（两套仪表因此全盲）。基准
首跑：open 臂 tick p50 **53.68ms**（alone 仅 2.8——先前"主要是原版底噪"的
判断错了，主耗是我们）。

**修法（HostBridge，从 VoxelAstar 拆出的宿主问询翻译层）**：贴身目标
（≤2.5 格同层）直接发两节点乐观存根；**按女仆限频**——十 tick 内已全额作
答的连环问询，同格复用原答卷、异格发存根；冷问询永远全额（诚实钉由此不受
影响）。全局"配额吃紧才存根"试过一轮即废：并行批次里配额常态吃紧，诚实钉
与杆桥的冷问询全被污染（sw215 七红）。疗效：open 臂 p50 53.68 → **4.62ms**
（贴平底噪），且收得更干净（left 0/240）。

**fenced 臂遗留**：单次规划仍到百毫秒级（栅栏=21 档车道弹道×BRAKE_FLOOR
512 的单价），配额限频下不炸 tick 但账面难看——方向：工作量感知的刹车地板
／跨规划弧线缓存，归余量专项。

**场景校准（sw219–220，实机口述回填）**：fenced 臂从"几排栅栏"改成
FencePen 家族的原景——**抬高一格的封闭圈＋西南角无栏台阶口**，物品均匀
撒进圈内外两侧。顺手抓出一个读数口径病：掉落物落地互相合并会吞实体，数
实体会把"合并"错记成"收走"（无女仆的 alone 臂一度"剩 58/240"）——
剩量必须按**件数汇总**。校准后判决：alone 臂 left 240/240（口径自证），
fenced 臂 **tick p50 2.41ms 不卡、她穿角口把圈内外收到只剩 15 件**。残余
账：单次规划约 61ms（p95 尖刺 243ms）——嫌疑从车道弹道转向 **mesh 兜底
雕刻不受 8ms 搜索刹车管辖**，归余量专项。

**杆桥连红的真凶：配额饿死（sw217–223 结案）**。四轮连红曾被记成"棋盘
轮盘"，直到三件取证工具就位才翻案：① `[probe-null]` 探路返空供词；②
`PathwalkTrace.probeAndOrder`——写单前先自己问一遍路并留档（探路答卷从
"全冻读数带反推"变成直接可读）；③ 修好两门**同款哑炮**——`Long.MIN_VALUE`
初值进 `nanoTime()/gameTime` 减法溢出成永远压声，`[voxel-quota]` 拒单日
志与 confess 限频器都这么哑过（sw217 整轮零供词差点把"toward 没被调用"
定成结论）。真相链：**探路（toward）不占配额名额、耗时却累进全局
nanosSpent** → 并行批次把 15ms/tick 烧穿 → 杆桥副本 moveTo 的执行侧
tryReserve 被拒，**手里无路时直接 return false** → sink 擦单进冷却，与
40 tick 写单周期相位锁死 → 原"连拒二十次强闯"保底要 800 tick、比场时还
长——**机制性饿死**，探路答卷却一直是完美的 4 节点 reach=true。修法一
刀：**拒单只许落在手里还有活路的身上**（沿旧路降级）；手里没路的立即放
行一次全额。sw223 判决：杆桥全族＋zigzag 四红齐愈，`[voxel-quota]` 开口
80 声（挤兑是真的，只是不再饿死人）。教训两条：日志限频器的初值永远别用
MIN_VALUE；"探路免费"的账最终会算到执行侧头上——免费与保底必须成对设计。

**沉门板案：谎报起点＋三层皆瞎（sw224–228 结案）**。饿死修好后浮出的
既有病：她站悬空下半门板上 160 tick 爬不上旁边的路。逐层取证（probe 探
针 → 读数带 → 现场实验 `[lid-edges]`）拼出全链：**t1 她还悬空**，
`standingOn` 够不着门板面（FOOTING_REACH 之外），`nearby` 的邻格回退把
起点解到**斜上方的石头格**——"凭空替她走一步"的原罪（AnchorResolver 自
己的 javadoc 里就写着这条禁忌）；从假起点铺出的 2 节点"有路"答卷让 sink
进入 RUNNING，**此后 moveTo 一次也不会再被调**（sink 只在边沿调 start），
影子路一直"活着"、走丢判定 1.28<1.5 永不触发——她以 walk 姿态对着 0.8
格的壁怼了 147 tick，直到差事耐心到点擦单才解围（重问立刻拿到真路：起
点=门板锚、CLIMB 登阶，两 tick 后起跳成功——只晚了 147 tick，超时判负）。
而落地后的门板锚本身**出边齐全**（现场实验证词：CLIMB/LEAP/DROP 一把，
0.81 贴脸登阶的 jumpOk 根本没拒——此前三个"仿真拒矮跳"的假设全错）。
修法两件套：**零位移看门**（`VoxelPath.dragging`：贴地执行中连续三十
tick 没挪半步就报废这条路——走丢量线距，量不到"贴着线原地怼"；三十
tick 比起跳酝酿长，不误伤）＋**影子同步撤路**（walker 报废后
`SureFootedNavigation.tick` 把影子一并清掉，sink 才会 isDone→重问）。
sw228 判决：stranded 自愈归绿。教训：**"有路在手"不等于"走得动"——执行
侧需要一层与规划无关的位移健康监测**；起点解析的任何回退都必须以"她一步
真能走到"为界。

**封圈风暴：不可达目标的连发全额审（sw230–235 结案，实机指认）**。玩家
搭了**封死的**栅栏圈、圈内外全是 P 点，她卡在圈边时服务器 22–44ms 持续
卡顿。复现进基准（sealed 臂：封圈+她在外+240 件全在圈内；ppoint 臂实测
plan 总账 14 秒/400 tick）。三层病因、五刀修法：① **mesh 兜底最贵**（每
次换件现雕 25×25 多边形网格、单价百毫秒、无缓存无预算）→ 雕刻按女仆缓
存（中心偏两格内、两秒 TTL——同格键会被沿栏蹭步穿透）＋耗时计入全局时
间账（`VoxelAstar.charge`）；② **512 节点确定性地板成了单价放大器**（栅
栏弹道图单节点贵，保底节点一次 150ms，8ms 刹车被架空）→ 生产规划的墙钟
硬顶统一为 **headroom：本 tick 时间预算的余额**（后置账拦不住正在爆炸的
这一单；良图 1–3ms 无感，毒图交诚实前沿分段收敛）；③ **差事退避跟不上
极端形态**（拉黑名单 8 件盖不住整圈 240 件轮流回锅）→ 上限 64。判决
（sw235）：sealed 臂 p95 190→28ms、ppoint 单价 99→3ms，**全场 508 测试
零红**。附带口径定案：**完备性钉审几何真理、直调引擎不限时（audit）；生
产链吃运行时预算、靠部分路分段收敛**——钉借 createPath 问路吃到 2ms 保
底而翻红（sw234）就是两个口径没分家的代价。工具教训追加一条：**py 补丁
脚本换行分隔时，脚本炸了轮照发**（sw231 四段修法全没落盘、跑了一轮纯对
照还当成疗效判决）——补丁落盘后必须 grep 验尸再发车。

**单价战争：从 150ms 到预算内（sw236–240，实机口径校准）**。玩家对
28ms p95 的追问（"无栅栏都在 8–9ms"）逼出最后一层真凶：**StrideWeb 的
弹道仿真缓存是实例字段，而每单 new StrideWeb=每单全部重仿真**——封圈案
93 次全额审每次 150ms，烧的都是同一批弹道；此前所有参数拉扯（预算 15→
8→12ms、粒度 32→8、mesh 预算闸）都在给它打掩护。主刀：**图缓存按女仆共
享**（HostBridge.webOf，探路与执行同一张，纯 TTL 两秒——挪窝不作废，锚
与弹道键本是绝对坐标、走到哪懒补到哪；挪两格整张作废的第一版把命中率打
回原形）。预算档随之分层定案：**新织的图（要现仿真，贵）吃 headroom 预
算档；缓存图上纯搜索便宜、永远全额**——绕行一次到位不退化（headroom 一
刀切曾把绕角口刹成贴墙蠕动、fenced 收货 235→127 腰斩），真无路的 null
让 sink 写 CANT_REACH、差事秒拉黑。sw240 终账：fenced p95 10ms、sealed
p50 1.8ms（残余 p95 54=缓存图上 no-route 全图扫的偶发尖刺，约一秒一次、
拉黑后静默；相比报案时的持续 22–44ms 是量级差异）。中途反复现形的教
训：**预算参数每收一档，都先看行为侧的账**——8ms 预算轮战斗对双红、拾
取吞吐腰斩，12ms 才是两头站得住的值；性能刀与行为钉必须同轮判读。

**原版对照定案（sw241，玩家提议）**：p95 44ms 的残余尖刺"风险大不大"，
让原版自己来作证——加 stockp 臂：同一个封死的圈、同一套拾取差事，导航
换纯原版链（TimedVanillaNavigation 只补记账；升级守卫是精确类匹配、不会
把它换回自有引擎）。判决：**原版 p95 46.21ms、规划总账 3009ms/70 次，比
我们（44.23ms、2253ms/51 次）还贵三分之一**——"不可达目标连发"的瞬时尖
刺是这类场景的天然价位：原版 A* 宣布无路同样要穷尽搜索预算，且它没有差
事拉黑、重问次数更多。结论：封圈场景我们已略优于原版，尖刺不是引擎回
归；再往下压属于"超越原版口径"的余量专项（no-route 负缓存、分期搜索）。
基准方法论沉淀：**性能争议先立原版对照臂——"贵不贵"永远是相对题**。

**轮盘再教育**：sw215–217 杆桥十二副本连红三轮，第九、第十个假设（重建微
差、存根污染）全错——sw218 仅修了一个**日志限频器**（纯观测）杆桥全数复
原。真相：新包/新批次洗了棋盘打包，未自清的邻居又轮流中奖。附赠一个工具
教训：**nanoTime 起点任意，拿 MIN_VALUE 当初值做限频会溢出成永远压声**
（sw217 的零供词就是这么哑的，差点把"toward 未被调用"当成结论）。
