# 战术改动实测记录

每一次改动、量到什么、留下还是撤掉。**改之前先查这里**——这份记录存在的唯一理由是不要把同一件事再试一遍。

## 规矩

- **结果指标在这个样本量下量不出小差别，机制指标才行。** 这条推翻了本文件早先写的"判据用 `dealt`，动 5 点算数"。那条规矩是拿三次基线（53.3 / 54.8 / 57.8）定的，而那三次凑巧靠得很近。后来**同一份代码跑两遍量到 58.7 和 41.1，差 17.6 点**；同配置的另一对是 64.3 和 56.3。所以：
  - **凡是差距小于约 20 点的 `dealt` 结论，一律不作数**，包括本文件里所有 ±5~8 的判断。
  - **机制指标里，分母小的那些一样是噪音。**"每支箭多少伤害"稳到小数点后一位，因为
    每局射出七到十二支；**"每刀多少伤害"不稳，因为每局只挥一到两刀**——十二局合计
    一二十刀，一次横扫或一次空砍就能把均值甩出五个点。R-19 实测：同一个开关关掉三次
    量到 8.37 / **14.00** / 8.47，打开三次量到 13.50 / **8.10** / 11.00，**关掉的那组里
    出现了全场最高值**。该比值一度被读作"暴击已生效"，与事实不符。<br>
    **看分母：每局出现七次以上的比值可以信，一两次的不能。**
  - **单靠一次 A/B 得出的差，一律当没测。**R-18 用一次 A/B 判了跳劈死刑（8.64 对 9.08），
    R-19 重复三次才看清那 0.44 完全在噪音里。**A/B 至少各跑两遍**，否则量到的是运气。
  - **"活多久"会污染几乎所有按局累计的量。**持剑 tick、在范围内 tick、每局挥击数，
    全都随她死得早晚一起缩水，不能当技术本身的证据。
  - **真正定位到问题的每一次，靠的都不是结果指标，是机制指标**：每支箭 3.30 点、起手 10.2 次对射出 8.9 支、够得着占 12%、持剑时平均间距 3.23 格、反编译出来的速度公式。这些量跨配置稳定到小数点后一位。
  - 存活数更不能用：同配置量到 2、3、2、4 / 12 和 4、8 / 24。
- **A/B 脚本的配置自检也会骗人。** 已发生三次：`grep "canStepOut) {"` 撞上另一处合法代码；`grep "sheddable ?"` 匹配不了跨行的三元表达式。**自检写错和实验跑错一样贵**，而且更难发现。
- **平时那一轮不跑基准。** `./gradlew runGameTestServer` 里基准整个跳过（
  `BenchmarkSwitch`，看环境变量 `COMPANIONSHIP_BENCHMARK`）。要读数时：

  ```bash
  COMPANIONSHIP_BENCHMARK=1 ./gradlew runGameTestServer
  ```

  实测把一轮从 **5 分 16 秒压到 2 分 23 秒**，164 条 required 全绿。
- **时间花在哪，量过才知道。** 一轮 4 分 48 秒的分布：启动 48 秒 → 146 条 required
  测试挤在两个 batch 里，**一共 25 秒** → 十八局基准，**3 分 35 秒** → 关服 20 秒。
  基准慢不是因为局数多，是因为**每局各占一个 batch，而 batch 串行**：一局卫道士
  1100 tick，一个 batch 就要十四五秒。先把局数从 24 / 12 减半，只省下三十秒——省掉的
  是 tick，串行的 batch 一个没少。**改对地方之前，先量清楚时间花在哪。**
- **两局都是四局**（2026-08-11：24 / 12 → 12 / 6 → 4 / 4）。一轮带基准约三分钟。
  **代价要说清楚：四局的 `dealt`、`存活` 一律不作数**，能看的只有量级差——R-20 的
  持剑 83t → 4t 是二十倍，那种才读得出来；几个点的差别在这个局数下没有意义。
- **四局的卫道士局，跨度能到 44 点。**同一份代码两次跑：输出 **84.5／存活 4** 与
  **40.2／存活 2**。这比早先记的 17 点噪音带还大一倍多——那条是十二局和二十四局量的，
  **局数减到四以后噪音跟着放大**。所以：**四局的卫道士局只用来看有没有崩，不用来
  比好坏。**要比好坏就上靶场那种分母（每局三四十次），或者把局数加回去。
- **局数变了，读数就不可比。**同一份代码，卫道士局持剑 tick 在 24 局时约 104–139、
  12 局时 58–184、4 局时 83。**别拿不同局数的两次读数作对比**，对照组必须同局数
  同一轮跑出来。
- 别用 `|` 当 A/B 脚本里 sed 的分隔符：Java 代码里到处是 `||`，会把表达式劈开。用 `#`。
- **配置对比串成一条无人值守命令**，A/B 各十二局。同一个仓库不能并行跑两次 GameTest：共用 `run-gametest/world` 和 Gradle 工程锁。
- 每条记录写**根因**，不写"调了个参数"。

| K-21 | 食物的"能不能吃"改问 Forge 的按实体属性；"吃了有什么"把有害效果计入定价 | **玩家报的一句话是两个独立的缺陷。**①**认不认得**：本体 `DefaultMaidWorkMeal.isWorkMeal` 用 `ItemStack.isEdible()`，读的是物品的**静态**食物属性；而 Forge 允许模组只实现 `getFoodProperties(stack, entity)`——按吃的人给属性。那类食物 `isEdible()` 恒为假，于是本体的处理器一个都不接，她眼里那根本不是食物。修法是在**本模组自己的**进食路径上加一个兜底处理器（不注册进 `MaidMealManager`，那是全局的，会连带改变其它工作模式），黑名单仍然照问。②**知不知道好坏**：`TlmFoodScanner` 只读 REGENERATION/ABSORPTION/HEAL，而 `FoodValue` 的紧凑构造器强制所有分量非负——**"吃了有坏处"在这个模型里根本无法表达**，毒马铃薯与面包一样免费。加 `harmSuffered`，毒/凋零按原版自己的掉血节奏折算，其余有害效果按时长记小账并**封顶两颗心**（不封顶的话腐肉那三十秒饥饿要记十五点，比她一半的命还多，于是"有点碍事"比"真的中毒"更可怕）。<br>**顺带炸出两个我自己埋的洞**：`EatingPolicy.duringALull` 挑"最便宜的一口"是按收益**升序**取最小，收益一旦能为负，这条排序就自己反过来直指毒的那个——排序没错，是"便宜"在有害食物出现之后不再等于"损失最小"；`whatTurnsTheFight` 用四参构造重建喂饱后的 `CombatCapability`，把 `guardedShare` 静默归零，于是被比较的两边不止差一口饭 | 定价这一半两层都钉住了：域内两条（`verifiesTheCheapestThingIsNeverTheOneThatHurtsHer`、`verifiesNothingIsBetterThanAMouthfulOfPoison`，都能在修复前复现出"她挑毒的那口"），端到端一条（`sheKnowsTheMouthfulThatCostsHer`，用原版毒马铃薯走真实的 `FoodProperties.getEffects()`，因为域内的 `FoodValue` 是手写的，"物品真的这么描述自己吗"只有那一层答得了）。那条同时断言它**仍然算食物**——把有害的藏起来不是认识它，那会让她守着一包腐肉饿死。<br>**认不认得那一半没有测试覆盖，如实记**：要造夹具就得有一个 `isEdible()` 为假、`getFoodProperties(stack, entity)` 非空的物品，而物品注册表在 GameTest 跑起来时已经冻结，本环境里造不出来。只有代码路径，没有断言 |

## 高低地形基准（2026-08-12）

卫道士局的地板从平板改成高低地形：台阶、两格高台、沟、两根柱子，位置写死以保证
读数可比。改动后立即复现既有失败——平地存活 2/4，高低地形 **0/4**。

**围墙是必需的，不是装饰**：竞技场抬高十二格而四周悬空，铺平时她没理由走到边上，
地形一加就有了。一局量到她与最近敌人差 **10.26 格**、寻路连续 **550 tick** 报走不到
——她被推出边缘掉了下去，那一局全部读数作废。

`TerrainTally` 六列，各回答一个不同的问题：高度差、走不到（`CANT_REACH_WALK_TARGET_SINCE`）、
卡住、绕路比、撞停、离地水平速度。**头四列一次性否掉了三条假设**：

| 假设 | 读数 | 结论 |
| --- | --- | --- |
| 地形拉长路径，速度比较全错 | 绕路比 **1.04–1.11** | 否，几乎等于直线 |
| 她卡在坎上走不到目的地 | 卡住 3–14t、走不到 ≤1t（共 700t） | 否 |
| 换手失败，剑取不出来 | 取出接口的失败计数全为零 | 否，差额全在"拉弓中按设计推迟换手" |

**真因是后两列量出来的**：`airSpeed ≈ 0.10`，只有走路速度的一半。

## 跳劈靶场：一个僵尸、五格、一把木剑

`JumpDojoGameTests`。跑法：

```bash
COMPANIONSHIP_DOJO=1 ./gradlew runGameTestServer   # 只跑靶场，约两分半
```

**为什么需要它**：跳劈前五轮改动全部失败，而当时唯一的验收手段是肉眼观察。
**没有一个数说得清她跳了没有、跳成了没有。**靶场只产出三个数——挥刀、起跳、暴击
——分母是冷却周期（每局三四十次），不是大基准里那一两刀。

**它一晚上找出七个错，四个在夹具、三个在判据。**夹具那四个尤其要记：

| 夹具错误 | 症状 | 真因 |
| --- | --- | --- |
| 竞技场没盖顶 | 僵尸第 69 tick 倒下，她只挥了 1.5 刀 | 露天自燃 |
| 木剑"够慢"是错觉 | 两刀就砍死二十血僵尸 | 她自己的攻击力属性叠在剑上面，再乘暴击 |
| 木桩血量拉到 2000 | 她**干脆不打**，三局各挥一刀 | 交战判据按敌人血量定价，两千血读作"打不赢" |
| 挥刀数用"每 tick 采样冷却上升沿" | 读到 1，同局起跳 42 次 | **冷却到期与下一刀常在同一 tick**，采样看不到那个空隙 |

最后一条是通用教训：**计数要长在被计数的那条路径上，不能在外面按 tick 采样。**
现在数在 `JumpLedger`，三个入口各一处。

判据那三个错见 K-11、K-12、K-13。

**三组场景（2026-08-11 扩到这个形状）**，一轮约三分半：

| 组 | 夹具 | 该看什么 | 实测 |
| --- | --- | --- | --- |
| `solo` | 一僵尸、五格、木剑，**八局** | 跳劈率该高 | **92–94%** |
| `pack` | 三僵尸围一圈 | **该接近零**——横扫比暴击值钱 | **0%**，起跳 0 次 |
| `axe` | 一个持斧卫道士，**会还手** | 血线压下来之后她还敢不敢跳 | **0–4%** |

`pack` 那一组的价值全在"答案是零"：一组只会说"是"的读数说明不了任何事，而它现在
**证明**了 `crowded` 那道闸是关着的，不是假设它关着。

`axe` 那一组直接量出了 `tooFrailToCommit` 的门槛该定在哪。八局对照，同一轮，
只翻那个常量：

| 门槛 | 跳劈率 | 起跳 | 挥刀 | 存活 |
| --- | --- | --- | --- | --- |
| 还挨得起 **2 下** | 0% | 0.1 | 3.9 | 7/8 |
| 还挨得起 **1.5 下** | **18%** | **3.4** | 4.9 | **7/8** |

两下太紧：卫道士一斧约 13 点、她有效生命 20 出头，`20 < 26` 恒成立，于是**在最需要
输出的那一局里跳劈整个是关着的**。放松到一下半，起跳从 0.1 涨到 3.4（三十四倍，闸
确实开了），而**存活一模一样**——这半下没有花掉任何命。已采用 1.5。

**这一段是靶场最该被复用的用法**：门槛这类取舍以前只能拍脑袋，因为大基准量不出来；
`axe` 组的分母虽然也不大（每局四五刀），但"起跳次数"这一列分母够、差距是数量级，
足以定一个常量。

| R-11 | T-06 拉到一半的弓不许丢（`CombatAppetite` 守弓） | 二十四局隔离：`dealt` 57.8 vs 基线 53.3/54.8——**只高出 3–4，在噪声带内**。而且它自称的机制被证伪：**箭伤反而从 28.5 掉到 25.0**，多留下的蓄力并没有变成箭。副作用是实的：吸收峰值 4.0 → 1.0，她几乎整局不吃东西（appetite 是无状态的，一个 21 tick 的蓄力周期里只剩一个 tick 的空档能起念头，起不中就这一轮不吃了）。**做不到自己说的事、又带着副作用，撤。** |

## 本体机制：弓的伤害与距离无关（实测 + 反编译确认）

`TaskBowAttack.performRangedAttack` 里就两行要紧的：

```java
float velocity   = Mth.clamp(distance / 10.0f, 1.6f, 3.2f);
float inaccuracy = 1.0f - Mth.clamp(distance / 100.0f, 0.0f, 0.9f);
arrow.setNoGravity(true);
arrow.shoot(dx, dy, dz, velocity, inaccuracy);
```

箭伤正比于 velocity。而**感知半径是 16，`distance/10 ≤ 1.6`，永远压在 clamp 的下限上**——
要超过 1.6 得站到 16 格外，要吃满 3.2 得站到 32 格外，两者都在她看得见的范围之外。

实测对上了：每局射出 8.9 支、箭伤 29.3 点，**每支 3.30 点**。也就是说她射出去的箭
**几乎支支命中**，弓已经跑在机制上限上了。

这条一次性推翻了几件事：

- **"站远一点箭更疼"不存在**（T-08 作废）。远近只影响精度，而精度在她用的距离上本来就够。
- **"箭被打断了"不存在**：起手 10.2 次、射出 8.9 支、满蓄力空等 0 tick。丢掉的蓄力
  1.4 次/局，14%，而且 R-11 那个守弓补丁没能改善它。
- **十五支箭封顶 49.5 点，只有全场 96 点的一半。**

于是账本变成这样，这才是要打的仗：

| | 上限 | 现在 |
| --- | --- | --- |
| 弓（15 × 3.3） | 49.5 | 29.3（只射出 8.9 支） |
| 剑（必须补足） | 46.5（约 5 下命中） | 26.0（2.5 下） |
| 合计 | 96 | 55 |

**剑必须打出一半以上，而她每局只挥 2.9 下**——持剑 90 tick、钻石剑每 0.63 秒一下，
本该有十四次机会。整晚都在优化弓，方向反了。

## 读数陷阱：死了以后每一列都还在数

`WEAPONS` 那行的 `empty[held=550t]` 曾被我读成"她空手站着大半局"，并据此改了代码。
**那是尸体。**她死于第 149 tick，`700 − 149 = 551`。同一局里活到底的对照是
`empty[held=6t]`。

`apples=0`、`arrows=0` 是同一回事——本文件早就为箭数写过"只在她活着的时候数"，
而 `empty` 这一列和苹果、箭都没享受到那条保护。

**判据：任何按 tick 累计的列，读之前先看 `diedAt`。**死亡时刻之后的每一 tick 都在
给"她什么都没拿"投票，而那正是尸体的定义。

**同一个陷阱在卫道士局的 summary 里换了个样子，我又差点走进去。**那一行的
`rootedTicks=560`、`stationaryWithFoes=558/700` 看起来像"她在战斗中发呆了八成时间"，
够吓人到让人立刻去改代码。但她死了，而这两列同样按 tick 累计：`engagedTicks=151`
加 `rooted=560` 正好是 700。**它们合起来只说明一件事——她约在第 150 tick 阵亡。**
死局里这两列不含任何关于"她战斗时在干什么"的信息。

## 夹具陷阱：`setNoAi` 不关重力，靶子会在半空中掉出感知

`aCrossbowFiresUnderTheRealOrchestrator` 与 `anEmptyCrossbowGivesWayToTheSword`
偶发地红，大约三次里有一次，症状是"两百 tick 一支箭都没出去"。我最初把它记到了
同期的食物改动头上——**那是错的**，对照组只有三次全绿，在三成的基础故障率下这本来
就有四分之一的概率发生。

真因在夹具，不在生产代码。两条测试都把靶子放在 `maid.getZ() + 6.0`，而房间地板只有
`5 × 5`；`setNoAi(true)` 关掉的是"它自己决定要动"，**关不掉重力**。房间抬高
`LIFT = 12` 格，而 `TlmThreatScanner.VERTICAL_REACH` 只有 6 格，于是靶子自由落体
约二十一 tick 之后就整个掉出扫描盒，她当场收兵。

**为什么只有弩会翻车**：弓二十 tick 拉满，弩要二十七 tick 装填，而靶子在第二十一
tick 前后消失——那根线正好从两者之间穿过去。所有用弓的同类夹具从来没红过，这不是
它们更健壮，是它们的表快了七 tick。

判读的关键一行是 `手里=crossbow 看见=0 只`：**她看见零个敌人**。同一条失败信息里的
定价行显示第 0 tick 时 `dist=6.0`、弩 1.97 胜近战 8.14，说明起手一切正常。一个只报
"没射出去"的断言对这种坏法完全免疫——它和"生产代码不开火"长得一模一样。

**顺手的那个修法是错的，而且量得出来。**第一版在 `placeInert` 里补了
`setNoGravity(true)`——看着正是"让它别动"。结果是**六次跑全红，每次两条**，红的还是
两条毫不相干的军械测试：`TlmThreatScanner.airborne` 把 `isNoGravity()` 直接读作"这只
在空中"，于是全套夹具里每一个靶子都被重新贴上离地标签，威胁定价整体位移。

**判据：靶子要保住重量，给它脚下补一块地板。**`CompanionScene.floorAt(x, z)` 只放
它站的那一块，不加宽整间房——这些房间本来就是从 `empty` 模板上摞出来的，加宽只会
往邻座的地盘上多摞几行。两条手写夹具同时改走 `placeInert`，它们此前还各自漏了
`setPersistenceRequired`。

## 本体机制：任何一次"用完物品"都会清空她的副手

`EntityMaid` 覆写了 `completeUsingItem`：

```java
protected void completeUsingItem() {
    this.getSwimManager().resetEatBreatheItem();
    super.completeUsingItem();
    this.backCurrentHandItemStack();   // ← 无条件
}
```

而 `backCurrentHandItemStack` 做的是：**把副手里的东西整个塞进背包**（塞不下就丢地上），
再把 `hideInv[0]` 放到副手。它服务的是本体自己的"临时换手吃饭"协议
（`memoryHandItemStack` 存、用完还），可它不检查这一次使用是不是走了那套协议。

于是任何在战斗中完成的物品使用——我们自己的进食走的是主手，与那套协议无关——
都会顺手卸掉她的副手。实测：一颗金苹果三十二 tick，随后 `offhand=empty` 持续
两百六十八 tick，盾牌读数三轮全零。

**结论不是"别在战斗中吃东西"，是副手不能当作稳定存放处。** 需要副手物品的功能必须
每 tick 确认它还在，不在就重新装备——`ShieldGuard.equipFromPack` 就是这条。同一条
约束适用于将来任何要用副手的东西。

## 本体机制：怪物一离地就走不动路（反编译确认）

`PathNavigation` 里两处同一道门：

```java
protected boolean canUpdatePath() {          // GroundPathNavigation
    return mob.onGround() || isInLiquid() || mob.isPassenger();
}

public Path createPath(...) {
    ...
    if (!canUpdatePath()) return null;       // 不站在地上，直接给 null
```

后果分两层，第二层才是要命的：

- `tick()` 里 `followThePath()` 被跳过，但**只要路还在**，末尾那句
  `moveControl.setWantedPosition(...)` 照常执行——所以带着一条活路起跳的怪，空中仍
  由 `MoveControl` 操纵，`LivingEntity.travel` 按 `flyingSpeed = 0.02` 给加速度。
- 可是**任何一次需要重新寻路的 tick 都会拿到 null**。`MoveToTargetSink` 起不来，
  在退出前 `eraseMemory(WALK_TARGET)`。战斗每 tick 都在改主意，于是"离地"几乎等于
  "把这一跳里的意图全丢掉"：她带着目的起跳，落地时手里什么都没有。

从外面看就是**跳一下白送一步**：她原地上下，敌人走近一格。这不是跳得不准，是这一跳
根本没被允许飞。补回来的东西写在 `AirControl` 里，只补原版拿走的那 0.02，不多给：
空气摩擦 0.91 每 tick 已经把它自然限制在约 0.2 格/tick，也就是走路速度。自己定一个
上限，等于让她在空中比她跟着的那个人还灵活。

## 本体机制：地面位移随速度的**平方**走（实测 + 反编译确认）

做闪避时踩到的，而且是踩了两遍。

`LivingEntity.travel` 在地面上的那条路径：

```java
float f3 = this.getFrictionInfluencedSpeed(f);   // = getSpeed() * (0.216 / f^3)
this.moveRelative(f3, travelVector);             // travelVector = (xxa, yya, zza)
```

而 `moveRelative` 里的 `getInputVector` 只在输入向量**长于 1** 时才归一化，短于 1
的按原样用。宿主的 `Mob.setSpeed(f)` 同时写 `this.speed = f` 和 `this.zza = f`，
于是那份速度**进了两次**：一次当缩放系数，一次当输入向量的长度。地面位移因此正比于
速度的平方，而不是速度。

两个后果，都是当场量到的：

- **只写方向不写速度，等于没写。** 第一版闪避只设了 `xxa`/`zza`，`getSpeed()` 是
  0，缩放系数就是 0——十二 tick 都写着方向，她横移了 0.02 格，然后被那一箭射中。
- **满速属性折出来接近每 tick 一格。** 女仆的 `MOVEMENT_SPEED` 是 **0.7**，倍率取
  1.0 时终端速度约 1 格/tick。第二版按飞行时间保持姿态，她一口气横移了**八格**，
  冲出了房间。计划 JSON 里那些 0.4/0.75 是**倍率**，平方之后才是她平时的样子。

> 教训不是"把常数调小"。同一个时长在她慢走和满速下差着一个数量级，而"让开半个
> 身位"在两种情形下是同一件事——**能用不变量表达的量不要用时长配平**。闪避因此改成
> 让够距离就收势，与她多快无关。

### 剑的漏斗：她冷却时站在自己够不着的地方

量出"她持剑时到底站在多远"之后，相关性是干净的：

| 局 | 持剑 | 平均间距 | 够得着 |
| --- | --- | --- | --- |
| 6 | 3t | **1.58** | 3t（100%） |
| 8 | 7t | **1.65** | 7t（100%） |
| 1 | 328t | **2.50** | 15t（5%） |
| 7 | 66t | **3.01** | 9t（14%） |

**2.43 = `threatReach 1.43 + safeGap 1.0`，分毫不差。**而她自己的攻击距离约 2.0。

`holdDistance` 只在"这一 tick 挥得动"时才去要 `strikeWindow`（约 1.75，够得着对方
而对方够不着她），冷却期的其余部分一律落到 `meleeHold` = **2.43，在她自己射程之外**。
于是每一个循环她都：走出自己的射程 → 站着等冷却 → 再走回去挥。那趟来回本身就吃掉
大半个冷却（0.68 格 × 2，冷却 12.5 tick），寻路稍有迟滞就赶不上下一刀。

**这才是 12% 的真正来源**，也解释了为什么 T-15、T-16 两次瞄准 `facingOneAtATime`
都纹丝不动——它根本不归那条规则管。

**"那就整个冷却期都站在 window 上"——试过了，更差，见 R-16。**当时的理由是"不损失
任何安全性：1.75 > 卫道士的 1.43"。错在 window 是**某一瞬间两个攻击距离的比较**，
而 `safeGap` 补的正是它漏掉的东西——**他们会动**。那三分之一格的优势只在她挥刀那一
tick 存在，在她挥不动的那一秒里对方走一步就吃掉了。实测：够得着 10%→27%，
**对方够得着她 25%→48%**，剑伤反而 31.6→17.8。

所以这一格的 10% 目前**没有已知的解法**。两个方向都堵死了：站近一点，暴露涨得比
产出快；退远一点或少退一点（R-14 / R-15），够得着的比例一分不动。

### 旧记录（漏斗的粗读）

```
持剑 90t → 在她自己攻击范围内 10t（12%）→ 其中不在冷却 2t
```

**她几乎从来不站在自己够得着的地方。**这不是冷却卡的，也不是没拿剑，是站位：
`MeleeSwing.holdDistance` 在"同时被一个以上够得着"时每 tick 都要一个能真正脱离
接触的距离，而四个卫道士让这个条件几乎恒真——于是她整场都在往后要距离，
既没退掉也没打到。**近战的代价付了，产出没收**（`hurt` 23.7，挥击 2.9）。

要点：这一格的绝对值要打折看。仪表量的是"离她最近的那只"，而她挥的是选中的
目标，两者不一定同一只，所以 10t 是下界；**12% 这个比例才是可信的部分**。

一整局的实际形状是：**远程阶段她赢（约 200 tick、九支箭、几乎不挨打），
近战阶段她输**（约 70 tick 内挨满 23 点倒下）。弓封顶两只，所以她每次都是
带着两只卫道士进近战，而近战每局只挥 2.9 下。

## 已知不可行 / 不要再试

- **感知半径 16 格**是很多东西的硬上限：远程站位被 `preferredRange=14` 卡住，永远拉不开射程 15 的骷髅；掠夺者（触及 16）会让裁决恒为 WITHDRAW。改它有两条路（单开敌意感知 / 整体抬高），都会导出完全不同的行为，**未定，不要自行选**。
- **金苹果不是 12 点**：伤害吸收 I = 4 点且**不叠加**，再生约 4 点。十个苹果远不到"120 点有效生命"。
- **掠夺者不能拿斧头**：它的目标列表里没有近战，会站着不动。要近战型劫掠者就用卫道士。

## K-11：交战判据从"数人头"改成"算价钱"（已留下）

`MeleeSwing.facingOneAtATime` → `canAffordTheExchange`。原来的规则是"同时被一个以上
够得着就脱离"，它**分不出两只僵尸和两个卫道士**——每秒 3 点和每秒 13 点，同一个数字。
在僵尸局它是对的（K-08 把挨打从 11.3 压到 1.08），在卫道士局同一条线让她整场只挥
2.5 下剑。把常量从 1 调到 2 也不行（R-15，`dealt` 27.9，整晚最差）。

改成两档，因为单一份额穿不过去：

```java
sheddable &= outruns(maid, threat.entity(), speed);   // 移速比 ≥ 1.5 才算甩得掉
double share = sheddable ? 0.15 : 0.50;               // 走得掉就严格，走不掉就站住
return landing <= effectiveHealth * share;
```

**她愿意在人堆里站多久，取决于走开有没有用。**僵尸 0.42/0.23 = 1.83，退就真甩掉了
（实测 `hurt` 1.08），所以按严格档、只站一个；卫道士 0.42/0.35 = 1.20，退了照样被
追上、23 点照挨还一刀不还，所以按宽松档站住打。这条也顺带给了金苹果一个它一直
没有的用处：吸收那 4 点会把她抬过"站得住一个卫道士"的线。

激进档取 0.5 而不是 0.4，是因为 0.4 正好卡在刀刃上：一个卫道士一次交手打出 8.125，
而 20 血的容许量是 8.000。**差 0.125，她掉一滴血答案就翻面。**

**实测：两道标尺都没有可辨的变化**（卫道士局 56.3 / 58.7 / 41.1 对基线 53.3 / 54.8 /
57.8；僵尸局 `hurt` 0.67 / 3.25 / 1.75 对基线 1.08，击杀持平）。以现在的样本量
**量不出它更好，也量不出它更差**。留下它的理由是规则本身成立——数人头分不出
那两种处境——而不是某个数字。

## K-12：进食按她自己的状态排序，不按饿不饿

玩家反馈三件事：状态掉了不补、打不过的敌人不提前补、补晚了。查下来是三个缺陷，
**都不是"防止她一直吃"那条**——扫描器把已生效效果记为零收益是对的，它不挡重补：

| 症状 | 根因 |
| --- | --- |
| 状态掉了不补 | `duringALull` 卡在 `hungerFraction ≤ 0.66`。**她不饿，唯一能在空档开火的规则就永远不开火** |
| 补晚了 | 那条规则还排在最前，而且专挑最便宜的 → 空档被面包占掉，苹果留在包里 |
| 打不过的不提前补 | `whatTurnsTheFight` 要求食物把裁决**翻成 ENGAGE**。打不过的仗没有食物翻得动 → 返回 null。**仗越难越不准备，逻辑是反的** |

改成 **快死了 → 身上的够不够扛住要来的 → 饿不饿**，新规则 `whileNothingCanReachHer`
问"护甲够不够"而不是"这口能不能让她赢"，并且挑**最便宜够用**的（T-14 那版挑最厚的，
一场吃掉 5.5 个苹果，手一直腾不出来）。

**翻掉了一条钉住的行为**：`verifiesAHopelessFightIsNotWorthTheStores` 原本钉着

## K-13：交战判据补上"几下能打死她"

K-11 的判据用 `damagePerSecond × exchange`——**一个平均速率，把"几下能打死她"抹平了**。
于是她算出"一个卫道士每秒 13 点，付得起"，而真相是两下。这正是
`EngagementRiskPolicy` 早就写下并改对过的那件事（`survivableBlowShare`），在下一层
被原样重犯了一遍。实机表现：一个卫道士两下就能杀死二十点血的女仆。"

```java
if (heaviest > 0 && mine < heaviest * MINIMUM_BLOWS_SURVIVED) return false;  // 3 下
```

不认识任何怪物：读她的有效生命和对方单次伤害，所以穿甲、吃了吸收、血更满都会诚实地
把她推过线。**核对过它不会误伤僵尸局**：那一局全程 `heavy=3.0`、她血量 20.0，
判据 `20 < 9` 恒为假，闸门从不生效——所以那一局击杀的波动与它无关。

顺带把这条判据从 `MeleeSwing` 拆成 `ExchangeAffordability`：它是"要不要站住对砍"的
策略判断，不是"怎么挥刀"的执行细节。**触发拆分的是又一次为腾行数去削无关注释**——
本文件早记过那是笔坏账，这次拆文件而不是再削一次。
